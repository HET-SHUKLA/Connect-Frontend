# 03 — End-to-End Encryption

> Shared design doc: duplicated in Connect-Backend and Connect-Frontend (`specs/03-e2ee.md`); keep both in sync. **This repo (Connect-Frontend) implements the cryptography**: key generation, key exchange, and frame encryption/decryption in the browser. The backend only relays key-exchange messages and hosts the public-key registry.

## Layers

1. **Transport (hop-by-hop):** DTLS-SRTP between each browser and the mediasoup transport. The SFU terminates this, so it alone does **not** make the system E2EE (report §8.4 acknowledges this).
2. **Frame layer (end-to-end):** each encoded audio/video frame is encrypted in the browser before SRTP, using `RTCRtpScriptTransform` + `public/e2eeWorker.js`. AES-GCM, 256-bit room key, 12-byte random IV prepended to ciphertext. The SFU forwards frames it cannot decrypt.
3. **Key distribution:** per-room symmetric key moved peer-to-peer over the signaling channel, wrapped with an ECDH-derived key.

## Key exchange protocol (as implemented)

- Each client creates an ECDH P-256 key pair per join and publishes the public key at `POST /api/keys/:peerId` (server keeps it in memory).
- First peer in a room (no existing producers) generates the AES-GCM room key.
- A joiner sends `request-key`; the server fans out `key-requested`; existing peers fetch the joiner's public key, derive `AES-GCM(ECDH)` and send `key-exchange {targetPeerId, encryptedRoomKey}`; the server relays it. The joiner uses the first answer.
- Existing peers also push the key to a new producer's peer when `new-producer` arrives.

## Known weaknesses (do not hide these in docs)

| # | Issue | Impact | Direction |
|---|---|---|---|
| E1 | Public keys are fetched **from the server** without authentication or fingerprints | A malicious/compromised server can swap keys and read the room key (active MITM) | Sign keys with user identity (auth service), or verify safety numbers/fingerprints in the UI; long-term: MLS (RFC 9420) |
| E2 | Worker **fails open**: without a key, or on encryption error, it forwards the frame **unencrypted** (`e2eeWorker.js`) | Silent loss of confidentiality | Drop frames / block publishing until the key is set; surface error in UI |
| E3 | Possible **split keys**: two peers joining an empty room concurrently each generate a key | Peers can't decrypt each other | Server-assigned "key leader" or deterministic first-joiner election |
| E4 | No key rotation when a peer leaves or joins | Leaver keeps decrypting; no forward/post-compromise secrecy | Rotate room key on membership change; consider SFrame / MLS |
| E5 | Frame format is custom, not SFrame (IETF draft-ietf-sframe-enc) | Interop/audit | Adopt SFrame when browser support allows |
| E6 | No authentication/authorisation on the signaling channel, keys endpoint is unauthenticated and unbounded | Anyone can register keys or probe rooms | Require JWT; scope `/keys` to room members; TTL entries |
| E7 | Browser support: `RTCRtpScriptTransform` isn't available everywhere | Calls fail or are unencrypted in unsupported browsers | Feature-detect and refuse to join without E2EE |
| E8 | Chat (when added) is not E2EE (report limitation; Signal Double Ratchet is future work) | | Encrypt chat with the room key as an interim step |

## Rules for agents

- The server must never receive a plaintext room key, private key, or decrypted frame; never log key material.
- Never add a code path where media is sent unencrypted after the user joined an "encrypted" room.
- Changes to `crypto.ts`, `keyExchange.ts`, `e2eeWorker.js` or the key-exchange messages require updating this file and calling out the security impact in the PR/commit.
- Do not describe DTLS-SRTP alone as end-to-end encryption in docs or UI copy.

## Frontend-specific responsibilities

- Fix E2 first: `public/e2eeWorker.js` must **fail closed** — drop frames (or block publishing) when no key is set or encryption throws; on decrypt failure drop the frame instead of passing ciphertext/plaintext through. Surface the state in the UI (the E2EE badge must only show "encrypted" when the worker has a key).
- Feature-detect `RTCRtpScriptTransform` before joining (E7); refuse to join an "encrypted" room without it.
- Zero key material in `console.*` logs, `localStorage`, URLs or error toasts. Keep the room key non-extractable after import (`importRoomKey` already uses `extractable: false`; the generated key must be exported only to hand to the worker/peers).
- Rotation on membership change (E4) and authenticated public keys (E1) need a spec + ADR before implementation, and a matching backend change (the backend owns the key relay).
